## 3. 格式能力对比（转述自 Phichain 文档 `[文档]`）

决定「编辑器支持到什么程度」「转换成什么格式」时可参考下表（✅ 支持 / 🔶 可用其他特性实现 / 🟡 计划中 / 🛑 不支持）：

| 特性 | Official | RPE | Phichain |
| --- | --- | --- | --- |
| Note / Event | ✅ | ✅ | ✅ |
| BPM 列表（变速） | 🛑 | ✅ | ✅ |
| 事件缓动 | 🛑（官谱只有线性） | ✅ | ✅ |
| 事件贝塞尔 | 🛑 | ✅ | ✅ |
| Elastic / Steps 缓动 | 🛑 | 🛑 | ✅ |
| 常量事件 | 🛑 | ✅ | ✅ |
| 父子判定线 | 🛑 | ✅（子线以父线为原点，**不继承旋转**） | ✅（除透明度外继承全部） |
| 曲线轨迹音符 | 🛑 | 🛑 | ✅ |
| 音符级事件 | 🛑 | 🛑 | 🟡 |
| 判定线材质 / 锚点 | 🛑 | ✅ | 🟡 |
| 假音符 / 事件层 | 🛑 | ✅ | 🟡 / 🟡 |
| 音符可见时间 / Y 偏移 | 🛑 | ✅ | 🔶（用音符级事件实现） |
| 缓动裁剪（easingLeft/Right） | 🛑 | ✅ | 🛑 |
| 元数据 / 扩展（故事板）事件 / 遮罩 / UI 绑定 / 音符透明度·大小·自定义打击特效 | 🛑 | ✅ | 🛑 |

另外，Phichain 的 RPE 导入器会**忽略**以下内容（可作为「哪些字段是渲染必需、哪些只是编辑器元数据」的参考）：`META` 中除 `offset` 以外的字段、`judgeLineGroup`、判定线的 `extended` / `father` / `numOfNotes` / 各 `*Control` / `zOrder`、事件的 `linkgroup` / `easingLeft` / `easingRight`、音符的 `alpha` / `isFake` / `size` / `visibleTime` / `yOffset`，并且**把所有事件层合并为一层**（即不支持层相加）。`[文档]`

> ⚠️ 与 Phira 文档的冲突点：Phichain 认为 RPE 子线「不继承旋转」，而 Phira 的 `rotateWithFather`（163+，缺省 false）允许继承父线旋转。**本项目的决定：采用 Phira 口径**（实现见 `docs/05 §4.5`、`docs/02 §3.2`）。

## 4. 本仓库的分析工具

### 4.1 `tools/inspect-chart.mjs` —— 谱面结构画像器

```powershell
node tools/inspect-chart.mjs "packages\白复生 AT（official格式）\Chart_AT #3649.json" > tools\profile-official.txt
node tools/inspect-chart.mjs "packages\领土战争AT（RPE格式）\29519800.json" > tools\profile-rpe.txt
```

输出内容（对两种格式通用，无需提前知道格式）：

- 根字段及其类型；
- 判定线的字段并集与「每个字段出现在多少条线上」；
- note 的字段并集、类型直方图、各数值字段的 min/max/不同取值个数；
- 每类事件的字段并集、条数、时间范围、缓动/贝塞尔/`linkgroup` 直方图、是否全局有序（用于判断是否符合事件规范）；
- `extended` 各扩展事件的字段与取值；
- RPE 专有：`META`、`BPMList`、`judgeLineGroup`、线条附加字段。

**注意**：Windows 下若用 `>` 重定向，PowerShell 可能写出 UTF-16LE 文件，导致后续按文本读取时报「二进制文件」。解决办法：用 `node ... > out.txt` 后执行一次 UTF-16 → UTF-8 转换，或让脚本自己写文件。

### 4.2 `tools/deep-check.mjs` —— 关键公式的数值验证

```powershell
node tools/deep-check.mjs      # 输出到 tools/deep-findings.txt
```

它做了两件事：

1. **官方格式**：用判定线的速度事件积分 `PJ(t)`，逐条比对 note 的 `floorPosition`，验证「`floorPosition = ∫speed d(秒)`」以及「与 note 自身 speed 无关」。
2. **RPE 格式**：扫描时间数组格式、分母集合、事件字段、`easingType` 取值范围、note 字段取值分布、`numOfNotes` 与类型计数的关系、速度事件取值集合等。

### 4.3 已生成的分析产物（可作为文档结论的证据）

| 文件 | 内容 |
| --- | --- |
| `tools/profile-official.txt` | 官方样本的字段画像 |
| `tools/profile-rpe.txt` | RPE 样本的字段画像 |
| `tools/deep-findings.txt` | 上述关键验证的原始输出（含逐条公式比对的结果） |

`tools/sample-colors.mjs` 可解码 PNG（8bit RGBA）并统计不透明主色与采样点，用于确认贴图颜色（`assets/` 的配色结论即由它得出）。

`tools/measure-trim.mjs` 测量每张贴图的「本体（不透明核心）bbox」与「光效外扩」，是 `src/render/textures.js` 中 `TEXTURE_TRIM` 表的来源（HL 贴图比普通贴图多约 40px 光效，不能算作体量）。
`tools/measure-hold-structure.mjs` 逐行打印 Hold 贴图的平均 alpha / 平均颜色 / 内容宽度，用于确定长条取样区段（证明纹理是「尾部白+低 alpha → 头部青+高 alpha」的平滑渐变）。
`tools/measure-notes.mjs` 从渲染截图里量音符的实际屏幕尺寸（确定默认音符宽度）。
`tools/hold-preview.mjs` 用纯 JS 光栅化把 Hold 的切片结果（新算法 vs 旧的错误算法）画成对照图 `tools/out/hold-preview.png`。
`tools/hold-variants.mjs` 出长条取样方案对照图 `tools/out/hold-variants.png`（帽高/取样段/纯色体/加法混合等）。
`tools/render-frame.mjs` **离屏帧渲染器**：软件光栅化回放 Canvas2D 的绘制指令并导出 PNG（无浏览器也能看渲染结果），支持 `--hold-sample`、`--note-width`、`--size`，配合 `tools/frame-sweep.mjs`（批量出帧）、`tools/hold-sheet.mjs`（长条样例表）、`tools/probe-frame.mjs`（像素探针）定位渲染问题。

### 4.4 抓取外部资料的办法（本机网络环境说明）

本机（沙箱）直连部分站点受限，实测可用/不可用如下：

| 主机 | 结果 |
| --- | --- |
| `docs.lchzh.top`、`teamflos.github.io`、`yuevuwu.github.io`、`mzh.moegirl.org.cn` | 可用（Node `fetch`） |
| `github.com` | 可访问页面，但 `raw.githubusercontent.com` 超时 |
| `data.jsdelivr.com`（列文件）、`gcore.jsdelivr.net` / `jsdelivr.b-cdn.net`（取文件） | 可用（**推荐用它读 GitHub 源码**） |
| `phichain.rs`、`cdn.jsdelivr.net`（主域）、`fastly.jsdelivr.net`、多种 gh 代理 | 超时/不可用 |

取 GitHub 源码的可用写法：

```js
// 列出仓库文件
await fetch('https://data.jsdelivr.com/v1/packages/gh/TeamFlos/phira@main?structure=flat')
// 取单个文件（注意路径要以 /gh/ 开头）
await fetch('https://gcore.jsdelivr.net/gh/TeamFlos/phira@main/prpr/src/parse/rpe.rs')
```

Windows 下 `curl`/`Invoke-WebRequest` 会因 schannel 凭证问题失败（`SEC_E_NO_CREDENTIALS`），请改用 Node 的 `fetch`；仓库里的 `tools/gh-raw.mjs` 把上面的镜像取法封装成了一行命令：

```powershell
node tools/gh-raw.mjs 'TeamFlos/phira@main' '/prpr/src/core/line.rs' out.rs
```

## 5. 待补齐的资料（需要人工确认）

1. 判定线长度的权威定义（Lchzh 实测 5.76H vs Phira 的 `lineLength = 6.0`）。
2. Phira 的 RPE 速度系数（约 0.267）与文档语义（2/9）相差约 20% 的原因。
3. 官方判定线颜色/宽度的最终值（不同版本可能有差异，建议多版本实测）。
4. RPE 1.7.0+ 与 170/更高版本新增的扩展事件与 note 字段（`textureEvents` 之类是否真实存在）。
5. 社区「统一格式」PhiCommonChart（<https://docs.nuanr-mxi.com/>，protobuf + `CompatLevel` 分层）是否需要支持——它是第三方标准，`[未验证]` 与 RPE/官谱的关系。
6. 官方 `PBC` 格式（Phira 支持但文档未完善）。
7. 官谱（official）是否已支持 `eventLayers` / `extended` 风格的新布局：本项目样本仍是扁平布局，Phira 的官方解析器也只认扁平布局。
